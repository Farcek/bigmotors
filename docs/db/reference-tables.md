# Лавлах хүснэгтүүдийн бүтэц

- Огноо: 2026-09-10
- Төлөв: Баталсан; Drizzle schema, constraint/index болон trigger source хэрэгжсэн. Эхний migration болон `0001_add_color_hex_code` local PostgreSQL 18 DB-д ажилласан. Seed болон lifecycle CRUD хийгдээгүй. [Хэрэгжүүлэлтийн зааг](../operations/db-schema.md).
- Үндэслэл: Анх 11 лавлах болон тоноглолын 1 холбох хүснэгт баталсан; дараа салбар/байршлыг салгаж 12 лавлах болгосон.
- Холбоотой баримт: [DB тойм](README.md), [Автомашины лавлах](vehicle-reference-data.md), [Сэлбэгийн лавлах](part-reference-data.md), [Дугуйн лавлах](tire-reference-data.md)

## Батлагдсан хүснэгтүүд

Доорх бүх лавлах нийтлэг 7 баганатай. Хамааралтай лавлахад эцэг лавлахын FK нэмэгдэнэ. Ерөнхий нэг `lookups` хүснэгтэд нэгтгэхгүй.

| Хүснэгт | Зориулалт | Нэмэлт багана / холбоос |
| --- | --- | --- |
| `vehicle_brands` | Автомашины марк | Автомашин болон сэлбэгийн нийцэлд дундын |
| `vehicle_models` | Автомашины загвар | `brand_id` UUID, заавал; `vehicle_brands.id` |
| `vehicle_variants` | Хувилбар / комплектаци | `model_id` UUID, заавал; `vehicle_models.id` |
| `vehicle_body_types` | Кузовын төрөл | SUV, sedan зэрэг; seed жагсаалт биш |
| `colors` | Өнгө | Гадна болон салоны өнгөнд дундын; сонголттой `hex_code` |
| `branches` | Компанийн салбар | Автомашин, сэлбэг, дугуйд дундын |
| `locations` | Бүтээгдэхүүн бодитоор байгаа байршил | Гурван төрөлд дундын; салбараас тусдаа лавлах |
| `vehicle_features` | Тоноглол, нэмэлт боломж | Нэг машин олон утга сонгоно |
| `part_categories` | Сэлбэгийн үндсэн/дэд ангилал | `parent_id` UUID, nullable; `part_categories.id`; үндсэн ангилалд хоосон |
| `part_brands` | Сэлбэгийн үйлдвэрлэгч / брэнд | Автомашины маркаас тусдаа |
| `tire_brands` | Дугуйн үйлдвэрлэгч / брэнд | Автомашин, сэлбэгийн брэндээс тусдаа |
| `tire_models` | Дугуйн загвар / цуврал | `brand_id` UUID, заавал; `tire_brands.id` |

2026-09-10: [ADR 0025](../adr/0025-separate-branches-and-locations.md)-аар салбар ба байршлыг салгасан. Одоо **12 лавлах + 1 тоноглолын холбох хүснэгт**. `locations` нийтлэг 7 баганатай; `vehicles`, `parts`, `tires` тус бүр `branch_id`, `location_id` гэсэн бие даасан холбоостой. Байршлыг заавал салбарт харьяалуулах FK байхгүй.

## Нийтлэг баганууд

| Багана | DB төрөл | Дүрэм |
| --- | --- | --- |
| `id` | `uuid` | Үндсэн түлхүүр; UUID үүсгэх арга тусдаа шийдэгдэнэ |
| `name` | `varchar(255)` | Заавал; лавлахын нэр |
| `description` | `varchar(512)` | Сонголттой тайлбар, nullable |
| `sort_order` | `integer` | Харуулах дараалал; default `0` |
| `is_active` | `boolean` | Идэвхтэй эсэх; default `true` |
| `created_at` | `timestamptz` | Үүсгэсэн огноо |
| `updated_at` | `timestamptz` | Сүүлд зассан огноо |

Лого, салбарын хаяг/утас зэрэг нэмэлт багана батлагдаагүй. `colors` нь нийтлэг 7 баганаас гадна доорх нэмэлт баганатай.

### Өнгөний HEX код

2026-09-10: Хэрэглэгч `colors`-т HEX код нэмэхийг хүссэн.

| Багана | DB төрөл | Дүрэм |
| --- | --- | --- |
| `hex_code` | `varchar(7)` | Сонголттой, default `NULL`; бөглөсөн үед `#RRGGBB`, жишээ `#FFFFFF` |

TypeScript талбарын нэр `hexCode`. Том/жижиг hex үсэг зөвшөөрнө; 3/8 оронтой код, `#`-гүй утга болон хоосон string-ийг DB хүлээн авахгүй. Хадгалсан утга яг `#RRGGBB` байна; PostgreSQL `varchar(7)` нь уртаас хэтэрсэн төгсгөлийн энгийн зайг өөрөө хасаж болно. Давхардлыг хориглохгүй: өөр нэртэй өнгөнүүд ижил дүрслэх кодтой байж болно. Өмнөх өнгөнүүдийн утга `NULL` хэвээр, автоматаар тааж бөглөхгүй. Nullable болон 6 оронтой формат нь өмнөх өгөгдөлтэй нийцүүлэх implementation сонголт.

Өнгөний shared CRUD/validation нь [ColorService](../operations/db-schema.md#colorservice)-д хэрэгжсэн; API болон өнгөний form хараахан байхгүй. API хэрэгжүүлэхдээ request/result-д `hexCode`-ийг дамжуулна. Service хоосон утгыг `null` болгон цэвэрлэж, засах хүсэлтэд талбарыг орхивол өмнөх утгыг хадгална. Admin-д өнгө сонгогч болон HEX input, харуулах үед өнгөний нэртэй хамт swatch ашиглана. `NULL` үед зөвхөн нэр харуулж, дурын өнгө таахгүй. Website мөн өнгөний нэрийг орлуулахгүйгээр HEX кодыг дүрслэлд ашиглана.

## Нэрийн давхардал ба хамаарал

- `vehicle_brands`, `vehicle_body_types`, `colors`, `branches`, `locations`, `vehicle_features`, `part_brands`, `tire_brands` дотор ижил нэр давхардахгүй. Салбар, байршлын нэр хоорондоо ижил байж болно.
- `vehicle_models`, `tire_models`-д ижил `brand_id` дотор нэр давхардахгүй; өөр брэндэд ижил нэр байж болно.
- `vehicle_variants`-д ижил `model_id` дотор нэр давхардахгүй.
- `part_categories`-д ижил эцгийн дотор нэр давхардахгүй; эцэггүй үндсэн ангиллын нэрүүд мөн хоорондоо давхардахгүй.
- `part_categories` өөрийгөө эцэг болгох, тойрог холбоос үүсгэхийг зөвшөөрөхгүй.
- Марк -> загвар -> комплектаци, дугуйн брэнд -> загвар гэсэн хамаарлыг хадгална. Хоорондоо зөрсөн сонголтыг зөвшөөрөхгүй.

Эдгээр нь батлагдсан дүрэм. Нэрийн том/жижиг үсэг, зай, Unicode normalization-ийн харьцуулалт болон nullable эцэгтэй uniqueness-ийг хэрэгжүүлэх SQL/index-ийн хэлбэрийг дараа нарийвчилна.

## Тоноглолын холбох хүснэгт

`vehicle_feature_links` нь лавлах биш, машин ба тоноглолын олон-олон холбоосыг хадгална. Дээрх нийтлэг лавлахын 7 баганыг энэ хүснэгтэд автоматаар нэмэхгүй.

| Багана | DB төрөл | Зориулалт |
| --- | --- | --- |
| `product_id` | `uuid` | Тухайн бодит машины бүтээгдэхүүний танигч |
| `feature_id` | `uuid` | `vehicle_features.id`-тай холбоно |

Хослол давхардахгүй, холбоос нь зөвхөн автомашинд хамаарах ёстой. Composite PK/unique болон `product_id`-ийн FK-ийн яг хэлбэрийг `vehicles` schema-тай уялдуулж нарийвчилна. Тусдаа тоноглолын бүлгийн лавлах нэмээгүй.

## Лавлахын lifecycle

Admin лавлах нэмэх, нэр засах, идэвхгүй болгох боломжтой. Ашиглагдаж байгаа лавлахыг шууд устгахгүй. Идэвхгүй лавлахын өмнөх холбоосыг хадгалж, шинэ сонголтыг хаана; бүтээгдэхүүнийг автоматаар нуухгүй. Өмнөх сонголттой бүтээгдэхүүнийг бусад шаардлага хангасан үед засах/нийтлэх боломжтой. Public нэр хэвийн, идэвхгүй тэмдэглэгээ зөвхөн admin-д байна.

Дэлгэрэнгүй lifecycle болон хамааралтай сонголтын шаардлагыг [нийтлэг дүрэм](../features/product-common-rules.md)-ээс баримтална.

## Баталгаажуулалтын зааг

2026-09-10-ны [нэгтгэсэн schema баталгаагаар](catalog-schema-proposal.md) UUID v4/DB үүсгэлт, timestamp update trigger, нэрийн trim + case-insensitive харьцуулалт, эцгийн хүрээний unique index, тоноглолын composite PK/FK болон RESTRICT delete арга тогтсон. Энэ нь дээрх нээлттэй техникийн сонголтын холбогдох хэсгийг орлоно. Schema/trigger source болон санах ойн тест болон migration хэрэгжсэн; бодит PostgreSQL concurrency тест хийгдээгүй. Seed, нарийн Unicode normalization болон admin permission matrix тусдаа хэвээр.

Нийт 12 лавлах + 1 холбох хүснэгтийн бүтэц батлагдсан. Түлш, хурдны хайрцаг, төлөв, валют, улирал зэрэг enum/const бүлэгт тусдаа admin-managed лавлах хүснэгт үүсгэхгүй; `packages/core`-д хөтөлнө. Энэ нь PostgreSQL enum эсвэл text + CHECK сонголтыг батлаагүй.

Нэмэлт 3 сэлбэгийн лавлах, дугуйн индекс/тэмдэглэгээний арга, seed өгөгдөл, admin permission matrix болон API нь тусдаа шийдвэр. FK delete/update action, индексийн яг хэлбэр, UUID үүсгэлт болон огноо шинэчлэх механизмын хэрэгжүүлэлт нээлттэй.

Drizzle schema болон migration дараагийн хэрэгжүүлэлтээр үүссэн; seed болон admin UI хийгдээгүй. Schema-ийн энэ баталгаа `docs.task.md`-ийн техникийн task-уудыг бүхэлд нь баталсан гэсэн үг биш.
