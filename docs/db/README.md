# Өгөгдлийн сан

Өгөгдлийн бүтэц, холбоос, бүрэн бүтэн байдлын дүрэм болон схемийн өөрчлөлтийг энд баримтжуулна.

## Технологийн сонголт

- Database: **PostgreSQL**
- ORM: **Drizzle ORM**
- Migration: **Drizzle migration workflow**

ORM сонголтыг [ADR 0003](../adr/0003-use-drizzle-orm.md), database болон migration сонголтыг [ADR 0005](../adr/0005-use-postgresql-and-drizzle-migrations.md)-д бүртгэсэн. Яг хувилбарууд, driver, schema-ийн бүтэц, файлын байршил болон migration команд хараахан тогтоогүй.

## DB бүтэц болон CRUD-ийн эзэмшил

Drizzle-д суурилсан **`packages/db` shared package** нь DB schema болон CRUD логикийг хариуцна. Үүнийг `web/website`-ийн сервер тал болон `sysop/server` хамт ашиглана. Байршил болон үүргийг [ADR 0013](../adr/0013-use-pnpm-workspace-layout.md)-д бүртгэсэн.

Бүх workspace package-ийн scope нь `@bigmotors/*`. Migration болон seed-ийн файл, логик, командыг мөн `packages/db` хариуцна. [ADR 0014](../adr/0014-use-bigmotors-scope-and-db-owned-migrations.md)-д баталсан.

Package exports, дотоод dependency-ийн бичлэг, DB package доторх файлын зам, driver болон ажиллуулах нарийвчилсан журам TASK-04-т нээлттэй. Schema, CRUD, migration болон seed-ийг app бүрд давхар хөтлөхгүй.

## Сервер талын хандалтын зааг

TASK-01-ийн архитектурыг [ADR 0015](../adr/0015-isolate-server-side-db-access.md)-д баталсан.

- `web/website`-ийн зөвхөн сервер тал болон `sysop/server` нь `packages/db`-г ашиглана. DB package нь app-уудаас хамаарахгүй.
- `sysop/app`, website-ийн client component, `sysop/dti` болон `packages/core` нь DB runtime кодыг шууд эсвэл дам импортлохгүй. DB код, driver, credentials browser bundle-д орохгүй.
- App тус бүр өөрийн environment/secrets-ээс connection тохиргоог авч, shared DB factory-д дамжуулна. DB package нь app-ийн environment-ийг өөрөө уншихгүй. Connection үүсгэх, дахин ашиглах, хаах lifecycle-ийг тухайн app удирдана.
- Website болон admin нь тусдаа PostgreSQL credentials/role ашиглана. DB түвшинд шаардлагатай хамгийн бага read/write эрх олгож, хэрэглэгчийн authorization-ийг сервер талд давхар шалгана. Shared CRUD ашигласан нь автоматаар бүх эрх олгохгүй.
- Driver/pool, factory signature, transaction болон CRUD API-ийн нарийвчлалыг TASK-04-т шийднэ. Өгөгдөл, үйлдэл тус бүрийн эрх болон нийтэд харагдах талбаруудыг дараа тодорхойлно.

Эдгээр нь батлагдсан архитектурын шаардлага; код, DB role болон bundle шалгалт хараахан хэрэгжээгүй.

## Баримтжуулах зүйлс

- Өгөгдлийн загвар, хүснэгтүүдийн холбоосын зураг (ERD)
- Хүснэгт, талбар, өгөгдлийн төрөл, тайлбар
- Анхдагч болон гадаад түлхүүр, заавал бөглөх болон давхцахгүй байх нөхцөл
- Индекс, хайлт болон шүүлтэд шаардлагатай бүтэц
- Схемийн өөрчлөлт (migration), эхлэх өгөгдөл (seed)
- Өгөгдөл хадгалах, устгах болон хувийн мэдээлэлтэй харьцах дүрэм

## Загварчлах үндсэн мэдээлэл

Төлөв: **Хэлэлцэж буй**. Хэрэглэгч schema-ийн хэлэлцүүлгийг эхлүүлж, бүтээгдэхүүний нэг бүртгэл юуг төлөөлөхийг тодруулсан. Хүснэгт, талбар болон constraint-ийн эцсийн бүтэц хараахан батлагдаагүй.

### Батлагдсан бүртгэлийн нэгж

| Бүтээгдэхүүн | Нэг бүртгэл юуг төлөөлөх вэ? |
| --- | --- |
| Автомашин | Тодорхой нэг бодит машин. Ижил марк, загвар, онтой хоёр машин тусдаа бүртгэлтэй байна. |
| Сэлбэг хэрэгсэл | Ижил бүтээгдэхүүний төрлийг төлөөлнө; олон ширхэг байж болно. Ширхэг бүрийг автомашин шиг тусдаа каталогийн бүртгэл болгохгүй. |
| Дугуй | Ижил бүтээгдэхүүний төрөл/хэмжээг төлөөлнө; олон ширхэг байж болно. Ширхэг бүрийг тусдаа каталогийн бүртгэл болгохгүй. |

Олон ширхэг байж болох нь үлдэгдлийн тоо хөтлөх, агуулахын хөдөлгөөн бүртгэх эсвэл сайтад тоо харуулах боломжийг баталсан гэсэн үг биш. Сэлбэг, дугуйг яг ямар үзүүлэлтээр ижил бүтээгдэхүүн гэж үзэхийг цаашид нарийвчилна.

### Хүснэгтийн бүтцийн санал

**Батлагдаагүй санал:** Нийтлэг мэдээллийг `products`, төрөл тус бүрийн мэдээллийг `vehicles`, `parts`, `tires` хүснэгтэд хадгалах. Энэ хувилбарт нэг бүтээгдэхүүн `products`-д нэг мөр, зөвхөн өөрийн төрлийн дэлгэрэнгүй хүснэгтэд нэг мөртэй байна. Сэлбэг/дугуйн олон ширхэг нь олон дэлгэрэнгүй мөр гэсэн үг биш.

Автомашинд `stock_quantity` ашиглахгүй байх болон өгөгдсөн VIN/арлын дугаарын давхардлыг хязгаарлах нь санал хэвээр. Нэгж автомашины мэдээллийн талбарууд, түүний дотор нийтлэлийн болон борлуулалтын төлөвийг ялгах шаардлагыг [талбарын баримтад](../features/vehicle-fields.md) баталсан. Энэ нь DB хүснэгт, багана, constraint-ийн бүтцийг баталсан гэсэн үг биш.

### Product-ийн жагсаалтын нэмэлт талбарууд

2026-09-09: Хэрэглэгч бүтээгдэхүүний жагсаалтын item-д ашиглах дараах нийтлэг талбаруудыг нэмэхээр тодруулсан. Автомашин, сэлбэг хэрэгсэл, дугуйд хамаарна; дараагийн DB schema боловсруулах үед product-ийн талбаруудад тусгана.

| Талбар | Зориулалт |
| --- | --- |
| `item_title` | Жагсаалтын item дээр харагдах гарчиг |
| `item_desc` | Жагсаалтын item дээр харагдах тайлбар |
| `item_image` | Жагсаалтын item дээр харагдах зураг |

Эдгээр нь жагсаалтын зориулалттай нэмэлт талбарууд; бүтээгдэхүүний дэлгэрэнгүй гарчиг, тайлбар, үндсэн зурагтай автоматаар нэгтгэхгүй. Нийтлэхэд `item_title`, `item_image` заавал, `item_desc` сонголттой; хоосон утгыг дэлгэрэнгүй мэдээллээс автоматаар орлуулахгүй. Ижил текст эсвэл зургийг сонгож болно. Текстийн урт болон зургийн хадгалалтын хэлбэрийг дараа шийднэ.

`item_*` болон автомашины 33 талбарын ноорог/нийтлэх нөхцөл, default, fallback дүрмийг [бөглөх шаардлагад](../features/vehicle-fields.md) 2026-09-09-нд баталсан. Энэ нь бизнес шаардлагын баталгаа; DB schema, migration өөрчлөөгүй. Нийтлэхэд заавал гэсэн шаардлагыг бүх мөрөнд `NOT NULL` тавихтай шууд адилтгахгүй: ноорогт дутуу мэдээлэл хадгалах боломжийг schema боловсруулахдаа харгалзана.

### Дараа нарийвчлах мэдээлэл

- Автомашин: марк, модель, он, үнэ, төлөв, техникийн үзүүлэлт
- Сэлбэг хэрэгсэл: бүтээгдэхүүнийг ялгах үзүүлэлт, part number, тохирох автомашин. [Талбарын санал](../features/part-fields.md)-ыг 2026-09-10-нд боловсруулсан; DB бүтэц болон бүртгэлийн нарийвчилсан дүрэм батлагдаагүй.
- Дугуй: брэнд, загвар, хэмжээ болон бүтээгдэхүүнийг ялгах бусад үзүүлэлт. [Талбарын санал](../features/tire-fields.md)-ыг 2026-09-10-нд боловсруулсан; үйлдвэрлэсэн огноо, хуучин дугуйн элэгдэл зэрэг ширхэг/нийлүүлэлтээс хамаарах мэдээллийн зааг нээлттэй.
- Сэлбэг/дугуйн үлдэгдлийн тоо хөтлөх эсэх, эсвэл зөвхөн бэлэн байдлын төлөв ашиглах эсэх
- Автомашины зураг: байршил, дараалал, үндсэн зураг
- Компанийн танилцуулга, үйлчилгээ, холбоо барих мэдээлэл

Эдгээр нь шаардлагаас үүдсэн анхны жагсаалт бөгөөд батлагдсан хүснэгтийн схем биш. Schema-ийн эзэн нь `packages/db` байна. Package доторх файлын бүтэц болон өгөгдөл/үйлдэл тус бүрийн эрхийг цаашид тодорхойлно; архитектурын заагийг дээрх хэсэгт баталсан.

## Хөтлөх зарчим

Схемийн өөрчлөлт бүрийн зорилго, нөлөөлөх өгөгдөл, шилжүүлэх болон буцаах аргыг тэмдэглэнэ. Бодит нууц үг, холболтын нууц мэдээлэл, хэрэглэгчийн хувийн өгөгдөл оруулахгүй. Нөөцлөх, сэргээх ажиллагааг [operations](../operations/README.md)-д баримтжуулна.
